🔴 Bug #1（严重）：非模拟模式下 LLM 对话历史被空占位消息污染
项目	内容
严重度	🔴 严重（核心功能退化）
文件	DiscussionContext.tsx
影响路径	所有关闭模拟模式、使用真实 API Key 的 LLM 调用
触发条件
用户在设置面板中配置了至少一个模型的 API Key 和 endpoint
用户关闭"模拟模式"开关（simulate: false）
用户输入话题并点击"发起"，开始真实 LLM 讨论
每一轮、每一个模型的 LLM 调用均会触发此 Bug
根因分析
generateResponse 函数中，非模拟路径（else 分支）存在明确的顺序错误：


TypeScript

// 第341-349行：先推送空占位消息

    id: msgId,
    role: 'assistant',
    content: '',          // ← 空内容
    modelId: model.id,
    modelName: model.name,
    round,
    thinking: true        // ← 标记为思考中
})

// 第350-351行：然后才构建 API 历史（此时 messagesRef 已含空占位）
controlRef.current.abortController = new AbortController()
const history = buildAPIHistory(model, round, topicRef.current, messagesRef.current)
对比模拟模式路径（第319-340行），顺序是正确的——generateSimReply 在 pushMessage 之前被调用，因此占位消息不会污染历史。

buildAPIHistory 函数遍历所有 assistant 消息并拼入历史，不检查 thinking 标志：


TypeScript

messages.forEach(msg => {
    if (msg.role === 'assistant') {
        history.push({ role: 'assistant', content: `[${msg.modelName}] ${msg.content}` })
    }
})
空占位消息 content: '' 被序列化为 {role: "assistant", content: "[ModelName] "}（模型名 + 空格），作为最后一条 assistant 消息出现在发给 LLM 的 payload 中，紧邻最终的 user: "现在轮到你发言了..." 提示。

预计后果
LLM 误认为自己已经发言：在模型的上下文中，它看到的最后一条 assistant 消息是自己发出的"空消息"，随后是"现在轮到你发言了"的指令，造成语义混乱
响应质量显著下降：模型可能输出续写、重复或混乱内容，而非新的独立观点
错误累积：后续轮次中，之前轮次生成的空占位内容虽然被流式填充了真实内容，但当前轮次推送给 LLM 的历史末尾永远有一条空占位，问题持续存在
核心功能失效：该应用核心价值是多模型观点碰撞与共识分析，LLM 响应质量下降直接破坏产品核心体验，且用户关闭模拟模式后无法获得预期效果
调试困难：用户无法从 UI 上看到发给 LLM 的历史，只能看到模型输出异常，但无法快速定位原因
修复方案
将 buildAPIHistory 调用移至 pushMessage 占位消息之前，与模拟模式的顺序保持一致：

将第 340-359 行的非模拟路径改为：

🟡 Bug #2（中等）：模拟模式下"跳过"按钮无效且给出误导性反馈
项目	内容
严重度	🟡 中等（用户可感知的功能缺陷）
文件	DiscussionContext.tsx、第319-339行
影响路径	默认模拟模式下的讨论流程
触发条件
默认处于模拟模式（simulate: true，即初始状态）
发起讨论后，在 AI 模拟打字逐字输出的过程中
用户点击"跳过"按钮
根因分析
nextSpeaker() 的实现为：


TypeScript

const nextSpeaker = useCallback(() => {
    controlRef.current.abortController?.abort()
    showToast('已跳过当前发言者', 'info')
}, [showToast])
该函数调用 abortController.abort()，但在模拟模式路径中（第319-339行），AbortController 从未被创建——new AbortController() 仅在非模拟路径（第350行）中执行。

模拟模式的逐字输出循环：


TypeScript

for (let i = 0; i < reply.length; i++) {
    if (!controlRef.current.active) return
    while (controlRef.current.paused) {
        await sleep(100)
        if (!controlRef.current.active) return
    }
    fullContent += reply[i]
    updateMessage(msgId, { content: fullContent, thinking: true })
    await sleep(20 + Math.random() * 30)
}
该循环只检查 controlRef.current.active 和 controlRef.current.paused，不检查 abort 信号。因此 abort() 调用为空操作（abortController 为 null，?.abort() 静默跳过），模拟打字动画继续执行直到全部内容输出完毕。

同时，showToast('已跳过当前发言者', 'info') 仍会执行，给用户造成"已跳过"的错误印象。

预计后果
用户点击"跳过"后看到 Toast 提示"已跳过当前发言者"，但发言并未被跳过
用户需等待约 5-15 秒（取决于回复长度和打字速度）直到模拟输出完成
属于误导性 UI 反馈，影响用户体验但不导致数据丢失或崩溃
修复方案
方案一：在 controlRef 中增加 skipRequested 标志位：


TypeScript

// 定义处（第179行附近）增加：
const controlRef = useRef({
    active: false,
    paused: false,
    skipRequested: false,
    abortController: null as AbortController | null
})

// nextSpeaker 中增加标志设置：
const nextSpeaker = useCallback(() => {
    controlRef.current.skipRequested = true
    controlRef.current.abortController?.abort()
    showToast('已跳过当前发言者', 'info')
}, [showToast])

// 模拟打字循环中增加跳过检查：
for (let i = 0; i < reply.length; i++) {
    if (!controlRef.current.active) return
    if (controlRef.current.skipRequested) {
        fullContent = reply
        updateMessage(msgId, { content: fullContent, thinking: true })
        break
    }
    // ... 原有逻辑
}
controlRef.current.skipRequested = false
方案二（更简单）：跳过时直接将 fullContent 设为完整回复并跳出循环，立即显示完整内容。

🟡 Bug #3（中等）：非模拟模式下"跳过"后消息永久停留在"思考中"状态

触发条件
非模拟模式（使用真实 API Key）

根因分析
nextSpeaker() 调用 abortController.abort() 后，streamChat 中的 fetch 因 AbortSignal 触发而抛出 AbortError。在 generateResponse 的 catch 块中：


TypeScript

预计后果

⚠️ 安全加固建议：Markdown 渲染未过滤 javascript: 协议链接
项目	内容
严重度	⚠️ 安全建议（需要特定条件触发）
文件	markdown.ts、MessageBubble.tsx
问题描述
AI 模型返回的 Markdown 内容通过 marked 库解析后，经 dangerouslySetInnerHTML 直接注入 DOM。虽然 markdown.ts 通过 walkTokens 对 html 类型 token 做了 HTML 转义，但未对链接/图片的 URL 协议做白名单过滤。

marked 默认会将 Markdown 链接 [click here](javascript:alert(document.domain)) 渲染为 <a href="javascript:alert(document.domain)">click here</a>。若 LLM 输出（或被 prompt injection 诱导输出）包含 javascript:、data: 等危险协议的链接，用户点击后可在页面上下文中执行任意 JavaScript。

由于用户的 API Key 存储在 localStorage（键名 prism_models，见 presetModels.ts:60），XSS 可窃取所有已配置模型的 API Key。

触发条件
需要 LLM 输出或被注入诱导输出含危险协议的 Markdown 链接，且用户点击该链接。由于本应用直接调用外部 LLM API 且不经过服务端内容过滤，prompt injection 是现实风险。

加固建议
在 marked 中自定义 link/image renderer，对 URL 协议做白名单校验：


TypeScript

marked.use({
    renderer: {
        link({ href, title, text }) {
            if (href && !/^(https?:|mailto:|tel:)/.test(href)) href = ''
            const titleAttr = title ? ` title="${escapeHtml(title)}"` : ''
            return `<a href="${href}"${titleAttr} target="_blank" rel="noopener noreferrer">${text}</a>`
        },
        image({ href, title, text }) {
            if (href && !/^https?:/.test(href)) return ''
            const titleAttr = title ? ` title="${escapeHtml(title)}"` : ''
            return `<img src="${href}" alt="${text}"${titleAttr} />`
        }
    }
})
或引入 DOMPurify 对 marked.parse() 的输出做统一消毒。
